## HW-07-09 — Padavan `mtd_storage.sh save` assumes `/tmp/hashes` exists

### Hardware symptom

During the successful live hotfix Storage save, Padavan printed:

```text
/sbin/mtd_storage.sh: line 89: can't create /tmp/hashes/storage_md5: nonexistent directory
```

but then continued with:

```text
Unlocking 'Storage' ...
Writing from '/tmp/storage.tar.bz2' to MTD 'Storage' ...  [ok]
Done.
```

Post-install audit confirmed `/tmp/hashes` did not exist.

### Relevant Padavan logic

`func_save()` performs roughly this order:

1. build the temporary Storage archive input;
2. run `md5sum -c -s $hsh` as a write-skip optimization;
3. if different, write `md5sum $tmp > $hsh`;
4. compress the archive;
5. validate compressed size;
6. call `mtd_write write ... Storage`.

On this hardware/runtime, the missing parent directory prevents only the volatile MD5 cache file from being created. The actual MTD write still completed successfully.

### v0.7.1 hardening

OURFW should not modify the vendor `/sbin/mtd_storage.sh`, but every OURFW-controlled call to Storage save should defensively ensure the volatile parent exists first:

```sh
mkdir -p /tmp/hashes 2>/dev/null || true
/sbin/mtd_storage.sh save
```

This avoids noisy errors and restores the intended unchanged-content write-skip behavior without patching the read-only Padavan script.

Add a regression/static check so OURFW save wrappers use the defensive helper rather than calling `mtd_storage.sh save` directly from multiple places.

## HW-07-10 — patched Smart ipset autoload is hardware-confirmed

After HWFIX1 was installed, the four ipset kernel dependencies were deliberately removed from the live router to prove the patched Smart path did not merely reuse modules loaded manually during earlier tests.

Preconditions:

- `ourfw_vpn4` and `ourfw_direct4` were destroyed;
- `ipset list -name` was empty;
- modules were removed in dependency-safe order;
- every `rmmod` returned `RC=0`;
- `/proc/modules` showed none of `nfnetlink`, `ip_set`, `ip_set_hash_net`, or `xt_set`.

The exact pre-arm proof was:

```text
IPSET_MODULE_CHAIN=ABSENT_OK
```

Then the patched `hy2-arm-smart` path was called. It returned:

```text
{"ok":true,"module":"vpn","operation":"hy2-arm-smart","rc":0,...}
ARM_RC=0
```

and all required kernel modules were present again automatically:

```text
xt_set ... Live
ip_set_hash_net ... Live
ip_set ... xt_set,ip_set_hash_net ... Live
nfnetlink ... ip_set ... Live
```

`hy2-status` simultaneously reported:

```text
NFNETLINK=loaded
IP_SET=loaded
IP_SET_HASH_NET=loaded
XT_SET=loaded
HY2_ROUTE=armed
MODE=smart
```

Policy route/table/TPROXY chain were correctly created for the temporary arm. The test immediately called `hy2-route-off` without confirming the route. Final hardware state was clean:

```text
HY2_ROUTE=off
ip rule = local/main/default only
table 101 = empty
OURFW_HY2=ABSENT_OK
```

No destination was placed in `ourfw_vpn4` during this autoload test, so no user traffic was selected for proxying while the route was briefly armed.

**Conclusion:** HW-07-01 is not only diagnosed; the live implementation of the intended fix is now hardware-proven on EC220-G5 v2 / kernel 3.4.113.
