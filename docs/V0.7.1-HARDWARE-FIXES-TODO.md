## HW-07-01 — Smart TPROXY does not load ipset kernel modules

### Symptom

On a clean boot/runtime, userspace `ipset v7.11` exists but:

```text
ipset v7.11: Cannot open session to kernel.
```

`hy2-arm-smart` returns `rc=5`; cleanup succeeds and leaves no stale `ip rule`, table 101 route, or `OURFW_HY2` chain.

### Root cause

`hy2-tproxy.sh::load_modules()` loads only:

- `nf_tproxy_core.ko`
- `xt_socket.ko`
- `xt_TPROXY.ko`

Smart mode checks that the `ipset` executable exists, but does not load the kernel-side dependencies required by `hash:net` and iptables `-m set`.

### Hardware proof

The stock/full image already contains compatible modules under `/lib/modules/3.4.113/kernel/net/netfilter`:

- `nfnetlink.ko`
- `ipset/ip_set.ko`
- `ipset/ip_set_hash_net.ko`
- `xt_set.ko`

Manual RAM-only load in this exact order succeeded (`RC=0` for all four). Then:

- `ipset create ourfw_probe hash:net family inet` -> `CREATE_RC=0`
- `ipset add ourfw_probe 1.1.1.1/32` -> `ADD_RC=0`
- iptables unreferenced test chain with `-m set --match-set ourfw_probe dst` -> `XT_SET_RULE_RC=0`

HWFIX1 later proved automatic loading on hardware after all four modules were deliberately unloaded first.

### v0.7.1 fix

For Smart mode, automatically load/verify:

```text
nfnetlink -> ip_set -> ip_set_hash_net -> xt_set
```

Do not require them for `vpn-all` unless actually needed. Extend status/diagnostics and CI regression checks so a future build cannot regress this dependency chain.

## HW-07-02 — subscription primary/backup selection corrupts another config key

### Symptom

Saving a primary/backup selection could write the node ID into:

```text
SUBSCRIPTION_LABEL_MAX_BYTES=<node-id>
```

instead of `SUBSCRIPTION_PRIMARY_ID` / `SUBSCRIPTION_BACKUP_ID`, making subscription config invalid.

### Root cause

BusyBox ash has no function-local variables by default. `set_selection()` stores the destination config key in global shell variable `key`, then calls `subscription_load_conf()`. `load_conf()` also uses the global names `key` and `val` while parsing every line. After parsing, `key` contains the final config key (`SUBSCRIPTION_LABEL_MAX_BYTES`), so `conf_set` updates the wrong field.

### Hardware workaround proven

Moving `subscription_load_conf` before the `case` that assigns `key` repaired selection on the live router. Both primary and backup then persisted correctly and `SUBSCRIPTION_LABEL_MAX_BYTES=160` remained valid.

HWFIX1 also hardened the common parser scratch variables; a later collision probe kept caller variables intact.

### v0.7.1 fix

Do both:

1. Make common config parser scratch variables collision-resistant (for example `_ourfw_conf_*`) instead of generic `f`, `line`, `key`, `val`.
2. Keep `set_selection()` ordered so config load happens before setting the write target.

Add a regression that actually performs **primary write + backup write** and asserts:

- primary ID is correct;
- backup ID is correct;
- `SUBSCRIPTION_LABEL_MAX_BYTES` remains `160`;
- no unrelated config key changes.

The CI test must stub/avoid real `mtd_storage.sh` writes.

## HW-07-03 — Hysteria startup API loses the useful failure reason

### Symptom

A failed `hy2-start-primary` / `hy2-start-backup` can return an unhelpful generic failure while `/tmp/ourfw/hy2/engine.log` contains the actual operational reason.

### Live HWFIX1/HWFIX1c result

The API now reports sanitized categories rather than raw subscription/engine material. However, category granularity is still imperfect: a controlled dropped endpoint was still classified `HY2_START_FAILED` instead of `HY2_CONNECT_TIMEOUT`.

### v0.7.1 fix

Return a **sanitized categorical reason**, never raw URI/auth material. Suggested categories:

- `HY2_CONNECT_TIMEOUT`
- `HY2_AUTH_FAILED`
- `HY2_TLS_FAILED`
- `HY2_CONNECTION_REFUSED`
- `HY2_NETWORK_UNREACHABLE`
- `HY2_START_FAILED`

Do not echo protected subscription URIs, auth tokens, obfs passwords, or full arbitrary engine logs through the WebUI API.

Add a deterministic unit test for classifier inputs instead of relying only on timing-sensitive live network failures.

## HW-07-04 — rapid Hysteria reconnects need cooldown/backoff

### Symptom

Both Hysteria endpoints are valid and hardware-confirmed, but rapid consecutive stop/start/retry sequences produced:

```text
connect error: timeout: no recent network activity
```

After a clean cooldown, a later attempt succeeded.

### Hardware proof

- primary `:1935` -> connected
- backup `:2096` -> connected
- both protected configs pass `-check-config`
- WAN and server IP remained reachable while transient Hysteria reconnect failures occurred
- HWFIX1 cooldown rejected an immediate retry and later allowed a successful primary restart
- successful restart reset cooldown to zero

### v0.7.1 fix

Add reconnect protection. A reasonable starting policy is exponential global startup backoff after actual network startup failures, e.g.:

```text
15s -> 30s -> 60s -> 120s (cap)
```

Reset the failure counter after a successful connection. Local validation/config/module failures should not unnecessarily trigger network cooldown. API/status should expose remaining cooldown without leaking secrets.

## HW-07-05 — no-flash WebUI reports base v0.6.3 instead of overlay v0.7.0

### Symptom

Plain runtime status was patched/live-tested to expose the overlay, but WebUI root status can still replace the page header with `v0.6.3`.

### Root cause

`status_json()` reads only `$OURFW/VERSION`, while no-flash deliberately keeps that file at `v0.6.3` to satisfy the immutable v0.6.3 loader. Feature version is stored in `$OURFW/VERSION.overlay`.

### Live HWFIX1 result

Runtime status now displays the overlay version while base `VERSION` remains untouched.

### v0.7.1 fix

Introduce one shared display-version helper:

1. use non-empty `VERSION.overlay` when present;
2. otherwise fall back to `VERSION`;
3. use the same helper in both text status and JSON status.

Do **not** change base `VERSION` on the v0.6.3 no-flash path.

## HW-07-09 — Padavan storage save expects `/tmp/hashes`

### Symptom

A valid OURFW storage save could produce a target-specific warning/error around:

```text
/tmp/hashes/storage_md5
```

because the Padavan storage helper assumes `/tmp/hashes` already exists.

### Live HWFIX1b proof

The live router changed only OURFW `save_storage()` to create `/tmp/hashes` before invoking `/sbin/mtd_storage.sh save`. After that:

- `/tmp/hashes` existed;
- `storage_md5` was generated;
- storage save completed successfully;
- no vendor `/sbin/mtd_storage.sh` patch was needed.

### v0.7.1 fix

Keep the compatibility shim inside OURFW:

```sh
mkdir -p /tmp/hashes 2>/dev/null || true
/sbin/mtd_storage.sh save ...
```

Do not modify the vendor helper in place. Add a target-runtime regression/stub that exercises a missing `/tmp/hashes` directory.

## HW-07-10 — WG/AWG profile parser is not portable to target BusyBox awk

### Symptom

A complete AmneziaWG profile was stored correctly and contained both `[Interface]` and `[Peer]`, but every required field appeared missing to OURFW and VPN apply failed with:

```text
vpn: WG/AWG profile incomplete
```

No `wg0` was created and no `awg setconf` log existed because failure happened before kernel/interface setup.

### Root cause

The section parser used:

```awk
gsub(/[[:space:]\[\]]/, "", s)
```

On the target BusyBox `awk`, this bracket-character-class construction did not normalize section headers as expected, so `cur` never matched `Interface`/`Peer`.

### Live HWFIX1d proof

Replacing section parsing with explicit operations:

```awk
sub(/^[[:space:]]*\[/, "", s)
sub(/\][[:space:]]*$/, "", s)
gsub(/^[[:space:]]+|[[:space:]]+$/, "", s)
```

made all mandatory fields visible on hardware:

```text
Interface.Address=PRESENT
Interface.PrivateKey=PRESENT
Peer.PublicKey=PRESENT
Peer.Endpoint=PRESENT
Peer.AllowedIPs=PRESENT
```

### v0.7.1 fix

Use the explicit BusyBox-safe parser in source and add tests executed under a BusyBox-compatible awk, not only host awk/gawk.

Include CRLF, comments, whitespace, optional PresharedKey, optional PersistentKeepalive, and AmneziaWG Jc/Jmin/Jmax/S1/S2/H1-H4 cases.

## HW-07-12 — external RU/Karing routing data needs a storage-safe ingestion path

### Current capability

OURFW Smart Routing is already present and hardware-tested. It consumes:

- `rules/vpn-domains.list`
- `rules/direct-domains.list`
- `rules/vpn-ips.list`
- `rules/direct-ips.list`

and dnsmasq maps domain resolutions into `ourfw_vpn4` / `ourfw_direct4` ipsets.

### Constraint found during live setup

The desired Karing/RunetFreedom datasets can be much larger than the EC220 persistent `/etc/storage` budget. Therefore v0.7.1 must **not** blindly save multi-megabyte public lists into persistent storage or WebUI textareas.

### v0.7.1 follow-up

Add an optional runtime rules-source/updater layer that:

- stores only source URLs, checksums/metadata and small manual overrides persistently;
- downloads large public lists into `/tmp` only;
- validates line format and imposes hard byte/entry limits before activation;
- builds/updates ipsets and dnsmasq-generated rules atomically;
- preserves small persistent manual FORCE-DIRECT/FORCE-VPN overrides;
- keeps last-known-good runtime data until a new download validates;
- never consumes the full `ru-blocked-all` class on this 64 MiB target by default.

Until this layer exists, use only compact persistent lists and manual overrides through the existing Routing WebUI.
