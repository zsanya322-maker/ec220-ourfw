# OURFW v0.7.1 — live routing/apply churn finding

Date: 2026-08-18
Device: TP-Link EC220-G5 v2
Baseline: v0.6.3 + HF1/HF2/HF3 + v0.7.0 no-flash overlay + HWFIX1/1b/1c/1d

## Finding

Changing only Routing configuration currently triggers the global `ourfw-apply.sh` pipeline, which reapplies every module in order:

`zram -> vpn -> smart-routing -> adblock -> dns -> nfqws -> watchdog -> diagnostics`

On a live AmneziaWG tunnel this is disruptive because `vpn/apply.sh` always calls `stop_ourfw_vpn` before starting the selected transport again. Therefore a Routing-only edit destroys and recreates `wg0`, forces a new handshake, restarts dnsmasq later in the same apply, and also tears down/recreates ZRAM unnecessarily.

The rollback path also reapplies the same full module set, so an unconfirmed candidate can cause a second round of tunnel/DNS churn.

## Hardware evidence from 2026-08-18 diagnostic

- 23:44:37 — AmneziaWG reached a valid handshake and was confirmed.
- 00:03:50 — Routing candidate changed to `vpn-all`; the existing `wg0` was destroyed and recreated even though VPN config did not change.
- 00:05:11..00:05:15 — rollback reapplied modules, destroyed/recreated `wg0` again, restarted dnsmasq, and returned routing to `smart`.
- 00:07:50 — candidate patch with compact routing list generated 486 dnsmasq rules; `wg0` was recreated again.
- 00:08:20 — Routing-only change back to `smart` again recreated `wg0` and restarted dnsmasq.
- 00:16:32 — another routing candidate again recreated `wg0`.
- 00:20:30 / 00:21:13 — additional full applies repeated the same tunnel, ZRAM and dnsmasq churn.
- 00:22:15 — VPN was deliberately disabled and `wg0` destroyed.
- 00:22:41 — routing was returned to `smart` and confirmed while VPN remained disabled.

No kernel crash or OOM was observed. The disruption is orchestration churn, not an AmneziaWG transport failure.

## Current post-diagnostic state

- VPN runtime disabled; no `wg0` runtime state file/interface.
- Routing config: `smart`.
- table 100 and table 101 empty; only local/main/default `ip rule` entries remain.
- `ourfw_vpn4` remains populated by dnsmasq with learned addresses; `ourfw_direct4` empty.
- mangle `OURFW_ROUTE` still marks destinations in `ourfw_vpn4`, but with no policy rule/table 100 the marks do not route into a VPN.
- kill-switch chain exists but has no active rules while VPN is disabled.
- AmneziaWG kernel module may remain loaded but is inert without `wg0`.
- Memory healthy: ~18 MiB free, ~22 MiB cache, full 15.5 MiB ZRAM swap free.

## v0.7.1 fix

Introduce scoped/transactional apply instead of unconditional full-stack reapply.

At minimum:

1. Routing-only candidate: apply `smart-routing` and only DNS when rule files/domain mappings changed; do not restart VPN, ZRAM, AdBlock, nfqws, watchdog or diagnostics unnecessarily.
2. VPN-only candidate: apply VPN, then routing/DNS only where required by tunnel/interface/DNS changes.
3. Rule-list-only candidate: update dnsmasq/ipsets atomically without recreating the tunnel.
4. Rollback must mirror the same scope and restore only affected modules/state.
5. Preserve the 90-second safety guard, but avoid causing a second unrelated transport restart on rollback.
6. Add live-state idempotence: if VPN type/profile/interface are unchanged and the current tunnel is healthy, `vpn/apply.sh` must not destroy/recreate it.
7. Do not reset/recreate ZRAM on every unrelated config commit.
8. Avoid restarting dnsmasq unless generated DNS configuration actually changed.

## Additional cosmetic bug confirmed

WG/AWG success log currently uses misspelled variable `VPN_INTFACE`:

`log "vpn: $type ready on $VPN_INTFACE"`

This produces lines such as `vpn: amneziawg ready on ` even though runtime state correctly records `wg0`. Fix to `VPN_INTERFACE` in v0.7.1 and add a shell regression.
