# v0.7.1 follow-up — HWFIX1e clear WebUI + scoped apply

Status: **source implementation prepared; live HWFIX1e package built and locally preflighted, not yet hardware-accepted on EC220 at the time of this note.**

## Hardware problem that triggered this fix

The 2026-08-18 router log showed that a Routing-only candidate was executing the legacy full apply chain:

`zram -> vpn -> smart-routing -> adblock -> dns -> nfqws -> watchdog -> diagnostics`

As a result, changing only Routing repeatedly destroyed/recreated `wg0`, performed a new AmneziaWG handshake, restarted dnsmasq and reinitialized ZRAM. The 90-second rollback repeated the same full-stack churn. The VPN tunnel itself was healthy; the lifecycle/apply granularity was wrong.

The same session also showed the imported routing-domain set was valid (`dns: generated 486 rules`), so the rule database was not the cause of the instability.

## HWFIX1e design

A new `runtime/ourfw-scope.sh` maps candidate tags to the smallest required runtime scope:

- Routing section -> `smart-routing dns`
- Routing mode only -> `smart-routing`
- VPN section -> `vpn smart-routing dns`
- DNS -> `dns`
- nfqws -> `nfqws`
- AdBlock -> `adblock dns`
- Watchdog -> `watchdog`
- ZRAM -> `zram`
- explicit advanced full apply -> legacy full stack

`ourfw-apply.sh` records pending tag/scope/start/deadline and applies only that scope. `ourfw-rollback.sh` reads the recorded scope before restoring last-good files and re-applies only the same scope.

## WebUI redesign

The normal UI now uses one primary save/apply action per section instead of separate immediate toggle buttons plus a second save path.

A prominent global candidate bar states that the change is already active but not persisted, shows the affected scope and countdown, and exposes only two decisions:

- **Keep and save**
- **Restore previous**

While a candidate is pending, additional settings commits are disabled.

Overview/status distinguishes saved configuration from real runtime state: VPN interface/tunnel state, WG/AWG handshake age, actual policy-rule presence, configured rule counts/current ipset counts, nfqws process state and ZRAM state.

Production polling remains conservative: initial load, explicit refresh, visibility return, post-action refresh, and ~2-second refresh only while a candidate is pending. The old permanent 15-second poll is not restored.

## Live package safety contract

`APPLY-OURFW-v070-LIVE-HWFIX1e.sh` is intended to replace only:

- `runtime/ourfw-scope.sh`
- `runtime/ourfw-apply.sh`
- `runtime/ourfw-rollback.sh`
- `runtime/ourfwctl.sh`
- `www/index.asp`
- `www/assets/ourfw.js`
- `www/assets/ourfw.css`

It deliberately does **not** overwrite live HWFIX1/HWFIX1b common runtime, HWFIX1c Hysteria runtime, or HWFIX1d VPN parser code. Installation itself must not invoke config apply, restart VPN/DNS/ZRAM, change routing, or reboot.

After physical installation, hardware acceptance should confirm:

1. HWFIX1e installer reports unchanged `ip rule` and table 100 state.
2. Routing save with AWG already up does not destroy/recreate `wg0`.
3. Routing rollback also leaves `wg0` intact.
4. VPN-section save restarts VPN exactly because VPN was the edited scope.
5. Pending banner/countdown tracks confirm and automatic rollback correctly.
