# OURFW v0.7.1 — clear WebUI + scoped safe apply

## Problem confirmed on EC220-G5 v2

The old WebUI exposed several independent buttons for the same setting (for example VPN enable/disable plus a separate VPN profile save, and Smart/vpn-all/off plus a separate Routing save). The user could not reliably tell whether a value was only edited, already active as a candidate, confirmed, rolled back, or currently active in runtime.

More importantly, every candidate used the same full `ourfw-apply.sh` module loop. A Routing-only change therefore re-applied ZRAM, destroyed/recreated the VPN interface, rebuilt Routing, restarted DNS, and re-applied unrelated modules. Rollback repeated the same full-stack churn.

Hardware logs proved repeated `wg0` destruction/recreation and dnsmasq/ZRAM reinitialization while only routing mode/lists were being changed.

## v0.7.1 model

### One editor action per section

Each normal settings page has one primary action: **Save and apply**. Enable/disable state is part of the same section form instead of a second immediate action.

- Routing saves mode + IPv6 + kill-switch + domain/IP lists together.
- VPN saves enabled state + protocol + profile + DNS/failover together.
- nfqws, AdBlock, Watchdog and ZRAM follow the same pattern.
- Full-stack apply is moved under Maintenance / Advanced and is not part of normal setup.

### Candidate state is global and obvious

When a candidate is active, a prominent bar is visible on every tab:

- the change is already active in runtime;
- the affected scope is named;
- the remaining auto-rollback time is shown;
- **Keep and save** confirms it;
- **Restore previous** rolls it back immediately.

While a candidate is pending, new settings commits are disabled so a second transaction cannot be accidentally stacked over the first one.

The status API exposes `pending_tag`, `pending_scope`, `pending_seconds`, and the last completed result (`confirmed` / `rolled-back`) so the UI does not infer state from button clicks.

### Runtime truth is separate from saved configuration

The Overview page reports live state, including:

- VPN configured vs actual tunnel/interface state;
- WG/AWG handshake age when available;
- routing mode vs actual policy-rule presence;
- configured domain/IP rule counts and current ipset entry counts;
- nfqws process state;
- ZRAM runtime state.

This prevents a saved checkbox from being presented as if the underlying service were actually running.

## Scoped apply map

`ourfw-scope.sh` maps transaction tags to the minimum required runtime modules:

| Scope | Runtime apply |
|---|---|
| `routing` | `smart-routing dns` |
| `routing-mode` | `smart-routing` |
| `vpn` | `vpn smart-routing dns` |
| `dns` | `dns` |
| `nfqws` | `nfqws` |
| `adblock` | `adblock dns` |
| `watchdog` | `watchdog` |
| `zram` | `zram` |
| `all` | legacy full stack |

Rollback records the scope before restoring the last-good files and re-applies only that same scope. A Routing rollback therefore does not bounce `wg0` or ZRAM.

## Refresh policy

The production UI does not restore the old 15-second background status poll.

Status is refreshed:

- once when the page loads;
- after explicit actions;
- when the tab becomes visible again;
- every ~2 seconds **only while a candidate is pending**, so the rollback countdown and final state stay accurate.

## Safety invariants

- The existing last-good config/profile/rules snapshot remains the rollback source.
- The rollback guard is armed before candidate installation.
- Confirmation still persists through `save_storage()`.
- A failed scoped apply invokes scoped rollback.
- HWFIX1e installation itself replaces runtime/UI files only; it does not invoke apply or restart VPN/DNS/ZRAM.
