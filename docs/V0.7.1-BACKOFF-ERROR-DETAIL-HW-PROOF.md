# OURFW v0.7.1 — Hysteria reconnect backoff / error-detail hardware proof

> Notes only. No v0.7.1 source code is implemented in this branch.

## Hardware test result

Physical TP-Link EC220-G5 v2, kernel `3.4.113`, live `v0.7.0-noflash-v063` with HWFIX1/HWFIX1b.

A temporary OUTPUT chain dropped only UDP traffic to the selected backup Hysteria endpoint on port `2096`. Hysteria routing itself remained off throughout the test.

### Controlled network failure

The temporary firewall rule saw one dropped Hysteria packet:

```text
DROP udp ... 213.176.64.151 udp dpt:2096
pkts=1 bytes=1286
```

`hy2-start-backup` then failed as intended:

```json
{"ok":false,"module":"vpn","operation":"hy2-start-backup","rc":1,"detail":"HY2_START_FAILED"}
```

Immediately after the failure, status showed:

```text
HY2_ENGINE=stopped
HY2_ROUTE=off
HY2_RECONNECT_COOLDOWN=13
```

An immediate primary reconnect attempt was rejected locally by the new backoff logic rather than attempting another QUIC connection:

```json
{"ok":false,"module":"vpn","operation":"hy2-start-primary","rc":9,"detail":"HY2_RECONNECT_COOLDOWN=11"}
```

A later status showed the countdown continuing (`HY2_RECONNECT_COOLDOWN=9`).

After waiting 17 seconds, the primary endpoint started successfully:

```json
{"ok":true,"module":"vpn","operation":"hy2-start-primary","rc":0,"detail":""}
```

and status returned to:

```text
HY2_ENGINE=running
HY2_ROUTE=off
HY2_RECONNECT_COOLDOWN=0
```

This proves on hardware that:

- a real startup network failure creates the first 15-second cooldown tier;
- immediate restart attempts are blocked locally with `rc=9`;
- the cooldown countdown is exposed by status/API;
- a successful later connection resets the cooldown state;
- the mechanism does not require Smart/TPROXY routing to be armed.

## Error-detail finding

The original v0.7 defect (`detail:""` on failed Hysteria startup) is partially fixed live: the failure now returns the safe non-empty category `HY2_START_FAILED`, so no secret URI/auth material is leaked and the API is no longer blank.

However, the controlled dropped-packet test did **not** classify as `HY2_CONNECT_TIMEOUT`. The reason is the current wrapper's own ~8-second startup timeout can terminate the engine before the engine log emits one of the strings used by `vpn/api.sh::hy2_failure_detail()`. The fallback therefore becomes `HY2_START_FAILED`.

### v0.7.1 / live follow-up

Make the Hysteria runtime itself emit a safe categorical reason at the point where it knows why startup failed, rather than relying only on post-hoc log parsing. At minimum:

- wrapper startup timeout -> `HY2_CONNECT_TIMEOUT`;
- process exits during startup -> `HY2_START_FAILED`;
- reconnect cooldown rejection -> existing `HY2_RECONNECT_COOLDOWN=<seconds>`;
- local protected-URI validation failure -> a safe config category (for example `HY2_CONFIG_INVALID`) if exposed to API.

The API should continue to sanitize and never return raw URI/auth/obfs material.

## Additional diagnostic memory finding

An earlier isolated test copied the 9,830,593-byte Hysteria binary a second time inside `/tmp` (tmpfs), reducing free RAM from roughly 16 MB to roughly 6.7 MB. The check process was then reported simply as `Killed`; kernel logs did not contain enough evidence to call this a confirmed OOM event.

Repeating the check with a hardlink instead of `cp` proved the safe approach:

- both paths shared the same inode;
- `/tmp` usage stayed at 9.9 MB;
- the known-good backup URI returned `CHECK_RC=0`;
- free memory and swap remained stable.

Future EC220 diagnostics must not duplicate large runtime binaries in tmpfs; use the existing binary or a hardlink when isolation is needed.
